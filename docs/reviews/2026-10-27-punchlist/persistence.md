# Persistence review (worktree `.worktrees/review` @ c374721)

Method: fresh SQLite and fresh Postgres 18 (SSL, scratch port 35821) migrated with `alembic upgrade head`, then `alembic check`. The production schema was compared column by column with a read-only `information_schema` query. Every module store was driven through its real source module: the Vite dev server ran on 35811 against the backend on 35801. Each store created a record with every field set, then updated it. A second signed-in browser context synced the store and compared every field. Behaviour scripts tested failure rollback, retry, the shared load notice, delete, relationships, rapid updates and two-tab edits. Scripts are in `scratchpad/persist/` (roundtrip.cjs, behaviour.cjs, notice.cjs, stale.cjs, tz.cjs, heir.cjs). Raw results are in `scratchpad/persist/roundtrip-results.json`.

## Checked and fine
- **Migration chain:** single head `e0f2a4c6b8d0`. `alembic upgrade head` succeeds on fresh SQLite and fresh Postgres 18. Prod `alembic_version` = `e0f2a4c6b8d0`.
- **Model vs prod, every table and column:** no model table or column is missing in prod. No nullability mismatch holds NULL data (checked `assets.is_closed`, `pulse_contacts.is_*`, `users.overwhelm_muted/onboarding_completed`: 0 NULL rows). The remaining type differences are varchar vs text and bytea only. Every model table is imported by `backend.main`, and `env.py` sees them all (no add_table in `alembic check`).
- **Round trip, create → update → fresh context, all fields equal:** vendors, home_access, utilities, letters, digital_assets, financial_assets (incl. valueHistory and camelCase columns), journal_entries, time_capsule, documents (object customAttributes), executor_steps, automation_rules, acceptance_tasks, visual_memories, funeral_data (nested wishes and budget), digital_guardian (user keys like `Some_Key`), advanced_assets, medical_profile, estate_profile (last4SSN), app_tone, scenario_settings, executor_sharing, estate_complexity, contact relationships.
- **Spelling-only differences (values survive):** subscriptions, heirlooms, timeline, pets, insurance, properties, calendar, contacts and medical_directives returned `custom_attributes` as `customAttributes` with identical JSON. `readCustom` (`utils/customFields.ts:7`) reads both. A custom-field edit on a server-read record persists (behaviour step 1). external_archives, family_memories and pulse_settings return camelCase. Their pages read both spellings or use `wirePayloadOfData` (`visual-memories/+page.svelte:93-94`, `pulse.svelte.ts` loadSettings). subscriptions `renewal_date` comes back as `…T00:00:00`, but the page uses `nextBilling` and `SubscriptionRow.svelte:22` normalizes it.
- **Camel/snake wire map:** every `/api/data` column survives `toWire(toCamel(col))` except `utilities.account_number`, which the utility mapper sends as snake (verified in the round trip).
- **Asset category membership:** properties, digital_assets and heirlooms list only their own rows (and a legacy NULL row in exactly one). A PUT through the wrong alias gives 404. Export uses the same `asset_category` rule (`routers/export.py:124-144`). Prod has 1 NULL-category asset.
- **Singletons:** unique `user_id` on funeraldata, advancedassetdata and digital_guardian_data in both prod and the fresh chain. GET returns one object (or `{}`) and POST upserts.
- **SyncManager behaviour:** an update failure (500) rolls the field back in memory and localStorage and shows one "Your draft is kept…" notice with Try Again. A singleton failure reverts (`bloodType` stays O+). Delete is gone in a second context and a 404 counts as removed. A contact delete cascades relationships on server and client. Five rapid updates to one row end at the last value. When five list and singleton reads fail, one shared notice appears; Try Again re-syncs all five and dismisses it. With the API unreachable at reload, the device copy shows instantly (pets and vendors counts kept).
- No backend ERROR or traceback in the server log across all runs.
