## Explicit limits

Origin/confirmed-ID tracking persists in the existing browser account/profile namespace, not a new server-side sample catalog. Browser storage refusal retains the marker in current-page memory through the existing persistence fallback, so cross-reload durability cannot be promised while device persistence is unavailable. No broader blocked-storage suite was added.

A late HTTP response rejected by `hooks.client.ts` before `post()` receives an ID remains uncertain; its A recovery retains origin, but its unknown existing server row is neither adopted nor purged. An actual ID reaching `post()` after a session change is marked only in its initiating namespace. The proof distinguishes these two boundaries.

The existing general timing limit remains outside X364: a current failed create is retained in memory and serialized at reset/account transition; a plain hard reload before that transition has no persisted recovery write. Baseline storage before logout was empty for that recovery. Existing pre-X364 recovery entries without origin are also left unclassified. No inference, legacy adoption, backfill or automatic purge of uncertain records was introduced.
